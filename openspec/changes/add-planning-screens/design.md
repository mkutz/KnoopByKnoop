# Design

## Context

- `modules/core` (Kotlin Multiplatform, JVM and iOS) already has the network graph, routing, the editable waypoint route (`route-planning`), the graph file format and the index with checksum verification (`network-data`). It does no I/O and no networking.
- `apps/android` (Compose) and `apps/ios` (SwiftUI, project generated by XcodeGen) only show a placeholder screen. Android consumes the core's JVM target, iOS links the static framework `KnoopByKnoopCore`.
- The pipeline publishes `index.json` and one graph file and one geometry file per region and network type in the rolling release `network-data`, under `https://github.com/mkutz/knoopbyknoop/releases/download/network-data/`.

## Goals / Non-Goals

**Goals:**

- Both apps behave the same, because the logic behind every spec scenario lives in the core and is tested there
- The platform code stays thin: storage, downloads, map rendering, screens

**Non-Goals:**

- Localization: the UI is English for now; region names come from a small table in the core
- Tablet layouts, accessibility beyond platform defaults, onboarding

## Decisions

### Shared logic in the core

New, I/O-free building blocks in `modules/core`:

| Building block | Responsibility | Covers |
|---|---|---|
| `RegionCatalog` | combines the index (or the cached index when offline) with the installed regions into a state per region: available, downloading, installed, updatable | List available regions, Update regions |
| `RegionInstaller` | checks downloaded bytes against their index entry and the supported format version, and returns the graph or the reason to reject it | Install only verified data |
| `PlanningSession` | the planning state machine on top of `Route`: tap a knot (start, end, stop into the best leg), move, remove, clear, switch network | Plan by tapping knots, Edit the waypoint list |
| `KnotLocator` | nearest knot within a radius in meters, backed by a grid index so taps stay fast on 38,000 knots | Tapping next to the network, Knots with equal numbers |
| `MapFeatures` | GeoJSON for knots, connections and the route along their course from `NetworkGeometry` (straight lines without matching geometry), plus the summary text (`12 → 7 → 45`, `3.5 km`) | Show the network, Show the route |
| `RouteSnapshot` | the current route as JSON (region, network type, waypoint knot IDs) and its restoration, reporting waypoints whose knots no longer exist | Keep the current route |

*Alternative:* each app implements planning on its own. Rejected, because the scenarios would have to be implemented and tested twice and would drift apart.

### Tap tolerance

The apps convert a touch target of 24 points to meters at the current zoom level and latitude, and ask `KnotLocator` for the nearest knot within that radius. Knots with equal numbers are distinct knots in the graph, so the nearest one is exactly the tapped one.

*Alternative:* MapLibre's `queryRenderedFeatures` around the tap. Rejected, because then the behavior of the scenarios would live in two map SDKs instead of tested core code.

### Map

- MapLibre on both platforms (Android SDK via Maven, MapLibre Native for iOS via Swift Package Manager): open source, vector tiles, and offline packs later.
- Base map: the OpenFreeMap "liberty" style, which is based on OpenStreetMap and needs no API key. Its attribution is shown as MapLibre's attribution control requires.
- The network is drawn from local GeoJSON sources, independent of the base map: connections as lines, knots as circles with their numbers as labels from zoom level 11, the route as a highlighted line on top. Offline, MapLibre shows the local layers on an empty background.
- Connections and the route follow the courses of the region's geometry file. Without geometry that belongs to the installed graph, `NetworkGeometry.straightLines` draws straight lines instead.

### Downloads and storage

- **Both platforms** download the graph and the geometry file of every network of a region, and install a network's two files together.
- **Android:** `DownloadManager` downloads in the background and resumes after connection drops. On completion, the app reads the file, lets `RegionInstaller` check it and moves it into app-private storage.
- **iOS:** a background `URLSession` download task, with the same check-and-move on completion.
- **Storage:** `regions/<region>/<network>.graph` and `<network>.geometry`, plus `regions/installed.json` with the installed index entries. Installing writes to a temporary file and renames it, so a region is never half-installed. The last index is cached for offline listing.
- **Current route:** `RouteSnapshot` JSON in app-private storage, written on every change.

*Alternative:* downloading in the core with Ktor. Rejected in `network-data` already: native background downloads are resumable and battery-friendly.

### Screens

- **Regions:** list with size, data date and state, a button per state (download, update, remove) and download progress.
- **Planner:** full-screen map with a network switch (cycling or hiking) and a bottom sheet with the summary and the waypoint list (drag to reorder, swipe to remove, clear).
- First start without an installed region opens the region list. Afterwards the app opens the planner on the last region.

## Risks / Trade-offs

- **Map performance with large GeoJSON sources:** the Dutch hiking network has 38,000 knots and 57,000 connections. MapLibre tiles GeoJSON on the device, which should be fast enough. If not, knots are filtered by zoom level, or the network becomes a vector tile source in a later change.
- **Dependency on OpenFreeMap:** a free service without guarantees. The style URL is a single constant, so another provider is a small change, and the network stays usable without it.
- **GeoJSON size with courses:** the Dutch hiking geometry has about 500,000 points. If drawing it all is too slow, connections are only drawn from a zoom level on, or simplified further for low zoom levels.

## Open Questions

None that change what gets built. Visual details (colors, zoom levels) are decided while implementing.
